# Задание для Codex: Keenetic Viva, Kakadu VPN, Discord и Smart DNS

Передайте агенту ссылку на этот файл и попросите выполнить задание ниже. Это руководство описывает диагностический подход, а не гарантированно работающую конфигурацию для любого провайдера.

## Цель и ограничения

Настроить стабильный доступ к ChatGPT/Codex и голосовым каналам Discord на домашней сети с роутером **Keenetic Viva**, установленным **nfqws2** и приложением **Kakadu VPN** на Windows. Сохранить работающий YouTube и другую необходимую пользователю функциональность.

Сначала проверяй DNS и устойчивость связи с Codex, затем Discord. Если во время работы Codex начинает регулярно переподключаться, приостанови Discord и сначала восстанови связь. Не обещай бесперебойную работу по итогам нескольких минут тестов.

Не предлагай мобильный интернет, не сбрасывай сеть и не отключай сетевые адаптеры. Изменения роутера, DNS, nfqws2 и VPN делай только при наличии разрешения пользователя; если пользователь уже разрешил конкретную работу, не спрашивай повторно. Перед изменением подготовь откат и поясни, что оно затронет. Не публикуй пароли, токены, логи учётных записей, скриншоты чатов и личные IP-адреса.

## 1. Установи, куда действительно идёт трафик

Kakadu VPN сам по себе не является причиной неисправности. Не предлагай удалить его и не отключай без необходимости. При полном VPN запросы с Windows могут уходить через зарубежный сервер и не показывать поведение домашнего провайдера. Проверь текущие маршруты, DNS адаптеров и возможность доступа к локальному адресу роутера.

Удобный вариант — оставить Kakadu включённым для связи с Codex и проводить сетевые запросы непосредственно **с роутера**, если SSH к нему доступен и его маршрут выходит через провайдера. Впоследствии реальные проверки Discord и работы Codex без VPN необходимо проводить на устройстве с прямым маршрутом. Отмечай, где и через какой маршрут выполнен каждый тест. Не считай принудительный IP или указание исходного интерфейса доказательством маршрута без проверки таблицы маршрутов и, при необходимости, трассировки.

## 2. Подключись к роутеру через терминал

В первую очередь используй штатные SSH и CLI, а не перехват управления браузером или графической панелью. Узнай адрес роутера, порты SSH и имена пользователей из действительной конфигурации или у пользователя, если их нельзя установить иначе. На Keenetic нередко есть отдельный доступ к CLI и отдельный доступ к оболочке Entware; не предполагай, что они находятся на одинаковых портах. Пользователь может сам ввести пароль в интерактивном запросе SSH: не проси присылать его в чат и не сохраняй его в репозитории или скриптах.

Начни с read-only проверок: маршрут роутера, действующая конфигурация DNS, профиль интернет-фильтра, установленные компоненты DoT/DoH, фактический процесс и запущенные аргументы nfqws2, правила очереди, действующие списки включения и исключения. Приложенный файл конфигурации может отличаться от запущенного процесса — проверяй оба.

Удобные команды Keenetic CLI, если доступны: `show ip name-server`, `show dns-proxy`, а для DNS-настроек — выборочная проверка `show running-config`. Не выводи полную конфигурацию без необходимости: в ней могут быть секреты. Пути Entware и имя интерфейса WAN нужно определить по устройству, не копировать из чужого примера.

## 3. Выбери Smart DNS и проверь всю цепочку

Сравни несколько актуальных Smart DNS, которые заявляют поддержку OpenAI. Обычные Google Public DNS или Cloudflare DNS не становятся Smart DNS только потому, что они отвечают на запросы. Сверь адреса и способы подключения с официальными страницами конкретных поставщиков.

Для каждого кандидата проверь:

1. Отвечает ли DNS с домашнего маршрута и возвращает ли он адрес прокси для доменов OpenAI. Учитывай, что некоторые поставщики выбирают ответ по географии IP клиента; ошибка базы геолокации может выключать проксирование.
2. Доступен ли каждый возвращённый адрес из домашней сети, устанавливается ли TLS с **правильным именем сайта и проверкой сертификата**, какой реальный ответ возвращается. Не называй HTTP 403 геоблокировкой автоматически: проверь, не является ли он проверкой Cloudflare. Для некоторых HTTPS DNS нужен HTTP/2; ошибка клиента, который умеет только HTTP/1.1, не доказывает неисправность сервера.
3. Работают ли необходимые домены авторизации, `chatgpt.com`, API и статических ресурсов. Для неавторизованного API ответ 401 может означать, что сервер доступен, но это не подтверждает полноценную работу аккаунта. Успешное открытие главной страницы не проверяет длительные ответы и переподключения Codex.

В одном другом подключении рабочим кандидатом оказался MagicDNS по DNS-over-TLS с отдельными правилами для `chatgpt.com`, `openai.com`, `oaistatic.com` и `oaiusercontent.com`, а также исключением этих доменов из hostlist nfqws2. **Не считай это готовым решением для Viva**: сперва проверь конкретный узел, его сертификат и выходной регион из сети друга. Несколько IP одного DNS-имени могут работать по-разному. Статический IP — потенциальная точка отказа, если оператор его сменит. Использовать чужой Smart DNS означает доверить его оператору DNS-запросы и метаданные соединений.

Если подбираешь профильные DoT/DoH-правила Keenetic для OpenAI, сначала проверь, как они взаимодействуют с существующим интернет-фильтром и обычными DNS: вывод CLI может обновиться с задержкой. Убедись, что другие домены, включая YouTube, продолжают разрешаться. Не смешивай несколько Smart DNS только ради резерва без понимания выбора сервера и того, как разные выходные узлы влияют на сессии. Сохраняй только проверенную конфигурацию.

Если Codex продолжает показывать reconnecting, изучи подходящие локальные диагностические журналы, исключив секреты и содержимое переписки из отчёта. Сопоставь время с DNS-запросами, сетевыми сбросами и настройками nfqws2. Записи `stream disconnected` или `connection reset` показывают срыв соединения, но сами по себе не определяют виновную сторону. Возможна конфликтующая стратегия nfqws2: проверь присутствие OpenAI в авто- и исключающем списках. При необходимости проведи краткий ограниченный A/B-тест с автоматическим откатом, не затрагивая YouTube и весь остальной трафик.

## 4. Диагностируй голосовой Discord

Попроси пользователя начать попытку подключения к своему голосовому каналу с устройства без VPN. Не отправляй сообщения и не присоединяйся к чужим разговорам от его имени. Просмотри свежие технические записи Discord, не публикуя содержимое чатов и секреты.

Определи, где прерывается соединение: DNS, TCP/TLS, управляющий WebSocket `*.discord.media`, авторизация, UDP IP discovery или обмен голосом. Запиши фактический порт и адрес текущего сервера. HTTP-код, TLS и WebSocket Upgrade проверяй раздельно; успешный WebSocket без авторизации сам по себе не подтверждает работу голоса.

На другом подключении сбой происходил на портах TCP 2053/2087 при установленном `--hostlist-domains=discord.media` и стратегии `--lua-desync=fake:blob=tls_clienthello:repeats=12:fooling=ts`. В контролируемом тесте этот же WebSocket проходил при временном обходе очереди nfqws2; после удаления этой одной строки из соответствующего TCP-профиля Discord подключился, а UDP-пинг отвечал. **Это только гипотеза для проверки**, не копируй изменение вслепую. Ранее в той же сети один из A/B-тестов тоже завершился сбросом: повторные измерения важны.

Если проверяешь влияние nfqws2 временными правилами, ограничь их конкретным клиентом, IP сервера и портом, зафиксируй счётчики срабатываний и обеспечь автоматическое удаление даже при потере SSH. Сравни базовое состояние, состояние во время обхода и после возврата. Не делай вывод по неработающему правилу без сработавших счётчиков.

Учитывай, что профили nfqws2 проверяются по порядку, и срабатывает первый подходящий профиль. Если меняешь конфигурацию, сохрани точную копию, проверь синтаксис и запущенные аргументы после перезапуска, предусмотрев автоматический откат. Сохрани YouTube и остальные рабочие настройки. В конце проверь состояние голосового канала и UDP-ответы, а пользователя попроси проверить слышимость в обе стороны.

## 5. Отчитайся о результате

Напиши, что реально изменено, какие проверки прошли и по каким маршрутам, где лежат резервные копии, что остаётся непроверенным и как отменить изменения. Различай факт восстановления соединения в тесте и подтверждённую длительную стабильность.
